Pokeplan on AWS

An event-driven pipeline that pulls PokeAPI into a lakehouse on S3 and builds the existing star schema with dbt. Each stage ends by publishing an event, and the next stage starts from that event, so each stage can fail and retry without the others.

13,671 resources per full load 10 facts, 16 dimensions London region (eu-west-2) Terraform walkthrough

How a run works

Two jobs, joined only by events. Orange dashed lines are events; black lines are work inside a job.

Step by step

  1. Every night at 02:00 a small function checks the PokeAPI data repository for a new version and publishes ingest.requested.
  2. Dagster picks that event up from a queue and starts the ingest job, which runs dlt to download the data into the raw zone on S3.
  3. When ingest succeeds it publishes raw.landed.
  4. Dagster starts the transform job. Soda checks the raw data first; if a check fails it publishes quality.failed, someone is alerted, and yesterday's tables stay in place.
  5. If the checks pass, dbt rebuilds the staging and mart tables and runs its tests, then publishes mart.refreshed. Metabase shows the new data.

Because the jobs only talk through events, a one-off backfill is just another ingest run, and re-running only the transform means publishing raw.landed by hand. Failed messages move to a dead-letter queue after three tries, and every event is archived for 30 days so a day can be replayed.

One tool per layer

The data is small (about 14,000 JSON documents, biggest table 638,000 rows) and changes a few times a year. The picks favour open-source tools that run inside the private network, plus AWS-native storage and security.

Ingestiondlt

Handles paging, retries and schema changes, and remembers what it loaded last time. Plain Python, so it runs as a container in the private network.

Also considered: Airbyte (has a PokeAPI connector but is heavy to host), Fivetran, Meltano. Kafka and Kinesis are left out because PokeAPI has no stream of changes to read.

StorageS3 + Apache Iceberg

An open table format on cheap storage, with a snapshot per load so you can look back in time or roll back.

Also considered: Redshift Serverless (closest to the Postgres SQL already written), Snowflake, BigQuery, Databricks.

Query engineAmazon Athena

Serverless SQL over Iceberg, paid per query, and dbt supports it.

Transformationdbt Core

Each existing SQL file maps to dbt models, seeds or tests (see "From Postgres to dbt").

Also considered: SQLMesh.

OrchestrationDagster

Treats every table as an asset with lineage, and reads the event queues to start runs.

Also considered: Amazon MWAA (managed Airflow), Step Functions, Prefect, Mage.

Data qualitySoda + dbt tests

Soda checks the raw load before anything is built. The 27 checks already written become dbt tests.

Also considered: Great Expectations, Monte Carlo.

DashboardsMetabase

Open source, behind a sign-in, reads the marts through Athena. The example queries become saved questions.

Also considered: Amazon QuickSight, Looker, Tableau, Power BI. Reverse ETL and Feast aren't needed yet.

GovernanceLake Formation

Controls which role can see which tables. The Glue catalogue plus dbt docs give a searchable catalogue with lineage.

Also considered: Atlan, Collibra, Privacera.

PokeAPI is public game data with no personal data, so GDPR only touches Metabase users and logs, and HIPAA does not apply. The security controls are still the production standard, because learning that is the point.

Network and security

Nothing inside has a public address. People come in through one signed-in front door; data goes out only to two websites.

Accounts and sign-in

  • Separate AWS accounts for prod, dev, security and logs.
  • People sign in through single sign-on. No long-lived keys.
  • Each job has its own role with only the access it needs.
  • GitHub deploys with short-lived tokens.

Protecting the data

  • A separate encryption key per data zone.
  • Buckets are private and only accept writes from inside the network.
  • Old versions kept, so any load can be rolled back.
  • Passwords live in Secrets Manager and rotate.

Watching for problems

  • Every AWS action logged to a locked logs account.
  • GuardDuty, Security Hub and AWS Config switched on.
  • Network and firewall logs kept.
  • Lake Formation records who queried which table.

Deploying

  • Everything is Terraform, reviewed in a pull request.
  • Container images scanned before use.
  • dbt runs against dev before prod.

From Postgres to dbt

The star schema already works on the full dataset, so this is a port, not a redesign. The main job is rewriting Postgres JSON functions in Athena's SQL dialect.

Today01_raw.sql

Becomes the raw Iceberg table that dlt writes. dlt's load ID replaces the load batch table.

Today02_reference.sql

Becomes dbt seeds: small CSV files for generation years, mechanic changes and form rules.

Today03_staging.sql

Becomes dbt staging models, one per current view.

Today04_marts.sql + 05_load.sql

Become dbt mart models. Facts rebuild in full each run (cheap at this size); dimensions update in place. dim_move stays a normal model because its versions follow games, not dates.

Today06_tests.sql

Becomes dbt tests: 27 that stop the run, 2 that only warn about known source quirks.

Today07_example_queries.sql

Becomes saved questions in Metabase.

Cost and build order

Nearly all the cost is network equipment that runs all month. The data work itself costs pennies. Prices are rough AWS list prices.

Production layoutAbout $800 a month
  • Network Firewall in two zones: about $580
  • Private connections to 12 AWS services: about $175
  • Two NAT gateways: about $65
  • Everything else: tens of dollars
Learning layoutAbout $70 a month
  • One NAT gateway
  • A DNS filter instead of Network Firewall
  • AWS services reached through NAT
  • Single database, Dagster off between sessions

Both come from the same Terraform with a settings file, so you can build the cheap one and still read the production one.

Build order

  1. Network: accounts, VPC, subnets and the outbound allowlist.
  2. Storage: buckets, encryption keys, Glue databases and Lake Formation grants.
  3. Run dlt from a laptop into the raw table, using a copy of the PokeAPI data repository as the first load.
  4. Port the SQL to dbt and get all 27 tests passing on Athena.
  5. Deploy Dagster and the event bus, queues and schedule, and switch to event-driven runs.
  6. Add the Soda checks, Metabase behind sign-in, and the alerts.
