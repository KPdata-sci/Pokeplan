How the API works

Read only, no auth

Only GET exists. No API key, no login. Every resource is public.

Rate limit and fair use

No rate limit since the move to static hosting in November 2018. The fair use policy still applies: cache resources locally every time you request them. Abusive clients get their IP permanently banned.

Resource lists and pagination

Call any endpoint without an id or name, e.g. /ability/, to get a page of up to 20 results. Change size with ?limit=60 and move with &offset=60. The response carries count, next, previous and results.

Named vs unnamed

Most endpoints accept {id or name} and list results as {name, url}. Five are unnamed and take only an id, listing {url}: .

Links between resources

Related objects arrive as a NamedAPIResource (name + url) or APIResource (url). The url always ends in /{id}/, which is the foreign key.

Shape quirks

/pokemon/{id}/encounters returns a JSON array, not an object; its URL comes from pokemon.location_area_encounters. Translated text (names, flavor text, effects) arrives as lists tagged with a language.

Reading this as a pipeline source

  1. Extract. For each endpoint, page the list with limit and offset (follow next until it is null), then fetch each detail URL.
  2. Land raw. Store every response as-is, keyed by endpoint and id. This is the fair-use cache and makes re-runs idempotent.
  3. Normalize. Turn each NamedAPIResource into a foreign key by parsing the id from its url. Explode lists such as names, flavor_text_entries and version_details into child tables.
